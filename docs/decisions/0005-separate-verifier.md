# 0005. Verification in a separate container from a clean base

## Context
The verdict is only trustworthy if the agent cannot read the tests and cannot influence the
grader. Running asserts in the agent's container fails both: the tests would be on disk, and
the agent could tamper with the interpreter, pytest, or startup hooks.

## Decision
`PytestVerifier.prepare` builds two images: a *verifier base* generated by the harness
(`FROM <environment>; USER root; RUN rm -rf <workdir>; USER <original>`) and the task's
`tests/Dockerfile` on top of it. `verify` starts a fresh container from the verifier image,
asserts the workdir is absent or empty, extracts the agent's workspace snapshot into it, and
runs pytest with `--rootdir` and `--confcutdir` pinned to `/tests`, without the workdir on
`PYTHONPATH`.

An earlier design masked the workdir with a tmpfs mount at run time. It was abandoned
because Docker's archive copy writes to the container's root filesystem beneath the mount,
and because a root-without-capabilities process cannot delete files it does not own, so
run-time cleanup is not reliable either. Deleting at build time is.

## Consequences
The agent's snapshot is the single agent-controlled input to grading; interpreter, packages
and tests all come from the image. Two extra small image builds per task (cached by
content-addressed tags). Task authors must keep tests under `/tests` and make the workdir
importable explicitly. A `sitecustomize.py` or `conftest.py` left by the agent is inert.
